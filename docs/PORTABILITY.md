# 可移植性调研：这套东西能不能换个 agent 宿主

结论先说：**页面、中继、票据/设备/审批那一层，本质上都是「通用」的；真正绑死 DSH 的只有一个文件里的一层「服务适配」。**
所以"移植"不是重写，是**写一个适配层**——但现在**不建议做**，理由在最后一节。

## 一、哪些是宿主无关的（可以直接搬）

| 部分 | 为什么无关 |
|---|---|
| `lib/page.html`（整站 UI，单文件零依赖） | 只认一份 JSON 契约与几个 HTTP 端点，不认识任何宿主概念 |
| `lib/sw.js` + manifest + 图标 | 纯浏览器侧 |
| `lib/ticket.js` | 只做「签发/兑换一次性票据」，HMAC + 受众 + 过期，与谁签无关 |
| 中继（`server.mjs`，私有仓库） | 只做转发、白名单路由、票据兑换、限流 |
| 设备账本、审计日志、高危动作两步确认 | 都在页面 + 一张表 + 一条策略里 |

## 二、哪些是 DSH 特有的

| 依赖点 | 具体是什么 |
|---|---|
| 读数据 | 会话列表、消息流、正在跑的状态、子代理、后台任务 —— 目前都从 DSH 的服务/文件结构里读 |
| 决策桥 | 两个 waterfall：`approval/request`（返回 `allowed-once` / `rejected`）与 `user-questions/request`（返回 `{answers:[…]}`） |
| 内容 | 附件/上传的收件箱约定、`/taskwatch/file` 的两个根（外加 v1.8.1 的会话引用白名单） |
| 事件 | `/taskwatch/data` 的字段形状、SSE 的推送格式 |

## 三、如果真要支持第二个宿主，适配层只需要四件事

1. **列出会话与消息**（含每条的 kind / 时间 / 工具名 / 文本）
2. **推送状态变化**（谁在跑、谁在等、谁失败）
3. **两个决策入口**：批准一次/拒绝，以及"回答问题"（没有就退化成只读）
4. **读取内容**：把某个被引用的文件按字节交出来（或明确拒绝）

剩下的（页面、票据、中继、设备、审计、高危确认、并行视图、相机、多入口）**一行都不用改**。
换句话说：`lib/index.js` 里真正绑定的只有「服务层」，页面那 5000 多行是与宿主无关的资产。

## 四、为什么现在不做

1. **用户在哪，产品就该在哪**：现在的用户全部在 DSH 上，做一个没人用的适配层等于把维护成本翻倍。
2. **抽象会过早**：第二个宿主的真实差异还不知道（比如它可能根本没有"审批"这个概念），现在设计的"通用协议"大概率是错的。
3. **成本不对称**：适配层不难，难的是**每个宿主的权限模型与安全边界都不一样**——我们花了 P4 整个阶段才把 DSH 这边的信任面收紧，换一个宿主等于从头来一遍。

**建议**：保持"DSH 深度集成 + 页面与中继保持宿主无关"这个现状。等真的出现第二个宿主、并且有真实用户在等，再按上面四件事写适配层；届时 `lib/page.html` / `ticket.js` / 中继都可以原样复用。

## 五、现在就值得做的一件小事

把 `lib/index.js` 里"服务层"与"路由/页面契约"**在文件里用注释分区**（不重构、不改行为），这样将来写适配层的人一眼能看出边界在哪。这条列进 P6，不单独发版本。
